## 1. Identifiers

### 1.1 Every entity has one immutable, meaningless key

| Rule | Reason |
|---|---|
| Primary keys are opaque text identifiers (`VIS-…`, `PHO-…`, `PRJ-…`), generated once and never changed. | A key that carries meaning eventually has to change when the meaning does. A meaningless key never does. |
| Identifiers are generated by a collision-resistant generator — `UNIQUEID()` in the capture layer, a UUID in backend services. | Sequential keys leak volume, invite guessing, and collide when two devices are offline at once. |
| A key is never reused, even after a row is cancelled or archived. | A reused key silently re-points every historical reference to it. |
| **Display codes are not keys.** `ProjectCode`, `LocationCode`, `ContractNumber`, `DocumentNumber` and filenames are for humans. Nothing joins on them. | `Block A` exists in two projects in the fixtures precisely so that a name-based lookup fails a test rather than a client (SEG-11). |

### 1.2 Prefixes

Each table's key carries a short prefix so that an identifier is self-describing in a log,
an error message or a support conversation: `LE-` legal entity, `PRJ-` project, `LOC-` location,
`VIS-` visit, `VAC-` visit activity, `PHO-` photograph, `SNG-` snag, `DOC-` document,
`JOB-` document job, `APR-` approval, `NUM-` number register entry, and so on. The full list is
generated into the data dictionary with an example per table.

The examples in the data dictionary deliberately do **not** resemble the fixture identifiers, so
that no example can ever be mistaken for real data — a rule the configurability check enforces
(CFG-01, CFG-02).

### 1.3 Foreign keys

- A foreign key stores the target's primary key and nothing else.
- Denormalised `ProjectID` appears on every project-scoped child row. It is redundant by design: row-level security must be decidable from the row itself, without a join the platform cannot perform inside a security filter.
- **A denormalised `ProjectID` must always equal the parent's.** Divergence is a defect, and `validate_seed.py` and SEG-10 both check it on every reference in the data set.
- A reference to a row in a different project is a cross-project leak and fails validation, even when both rows are otherwise valid.

### 1.4 File references

Files are addressed by the storage provider's own file identifier, never by path or name. A file
that is moved, renamed or reorganised keeps the same identifier, so no database reference breaks
(P-11). Until a production connection exists, these columns hold synthetic references — in Phase 1
nothing is connected (D-14).

## 2. Versioning

`EntityVersion` starts at 1 and increments on every **material** change — the same definition of
material used by the content hash, so the two can never disagree.

Each increment writes an `EntityVersions` row recording the version, the hash, who changed it, when,
which hashed fields changed, and which approvals the change invalidated. That row is the answer to
the only question that matters during a dispute: *what exactly was approved, by whom, and has it
changed since?*

`EntityVersions` also records `CanonicalFieldSetVersion`, so a hash computed under an older field
set is still interpretable years later.

## 3. Content hashing — the definition of "material"

### 3.1 Why this needs a definition at all

§5.18 requires that a material edit after approval invalidates downstream approvals. "Material" was
undefined, and the definition is the whole difficulty:

- Hash **everything**, and a timestamp or an internal comment voids an approval. Reviewers re-approve constantly, stop reading, and the control becomes theatre.
- Hash **nothing**, and content changes silently underneath an approval.

So the canonical field list is published, versioned, and reviewable — a decision, not an
implementation accident.

### 3.2 The algorithm

```
ContentHash = SHA-256( canonical_string )

canonical_string = join(U+001F, [ "Field=value" for each field in content_hash_fields ]
                                + [ "ChildLabel=[h1,h2,…]" for each folded collection ])
```

Normalisation rules, each of which exists because its absence causes a false difference:

| Rule | Prevents |
|---|---|
| Only the fields in `content_hash_fields`, in that exact order. | Field-order changes producing a new hash for identical content. |
| Text NFC-normalised and trimmed. Arabic normalised, **never transliterated**. | Two visually identical strings hashing differently (HASH-10, LNG-07, LNG-08). |
| `NULL` and `""` produce the same canonical value. | An empty field differing from an absent one by accident (HASH-09). |
| Decimals quantised to the column's declared scale. | `1200` and `1200.000` being treated as different quantities (HASH-11) while `1200.001` still differs (HASH-12). |
| Dates `YYYY-MM-DD`; datetimes ISO-8601 UTC with `Z`; booleans `TRUE`/`FALSE`. | Locale and formatting drift. |
| Child collections folded in as an ordered list of child hashes. | Re-ordering or adding an approved photograph passing unnoticed (HASH-07, HASH-08). |

### 3.3 What is included, and what is not

**Included — fields that determine the output a client sees:** project, location, work order, dates
and times, weather, supervisor, descriptions in both languages, safety observation, client
representative and acknowledgement claim, activity type, quantity, unit, percent complete,
supervisor confirmation, evidence stage, captions in both languages, approval for report, report
sequence, and the ordered set of approved photographs.

**Excluded, deliberately:**

| Excluded | Why |
|---|---|
| `UpdatedAt`, `UpdatedBy` | A save with no content change must not void an approval (HASH-04). |
| UI ordering and display fields | Presentation is not content. |
| Internal reviewer comments | Commentary about the record is not the record. |
| **Every advisory AI field** — `AIObservation`, `AIConfidence`, `AIAnalysisStatus`, `AIModel`, `AIPromptVersion`, `AIContradictsCaption` | **An AI observation arriving after a human approval must never void that approval** (D-06, HASH-05, GOV-09). AI assists the reviewer; it cannot overturn them. |

### 3.4 What a hash mismatch means

Before any release, any accounting posting and any send, the hash is recomputed and compared with
the hash recorded on the approval.

- **Match** — the approval still applies. Proceed.
- **Mismatch** — the approval is `Void`, with `VoidedAt` and `VoidReason` recorded, and **every approval downstream of it is void too**. The document moves to `RevisionRequired` and a new revision is created. Nothing is overwritten; the superseded revision remains.

This is what makes §14 criterion 11 testable rather than aspirational.

### 3.5 Changing the canonical field set

Changing which fields are hashed changes **every** hash in the system. It is therefore a schema
migration with its own decision record and its own `CanonicalFieldSetVersion` increment — never a
quiet edit. Existing approvals are re-evaluated under the version they were made with.

## 4. Audit trail

`AuditLog` is append-only for **every** role, including both administrator roles and break-glass access (GOV-07). No update or delete
path exists anywhere in the security matrix (GOV-06).

Each entry records: UTC timestamp, actor (user or service), action, entity type and identifier,
project, before and after hashes, source device or address where genuinely available, correlation
identifier, result, and reason. It never records an access token, a credential, or a full sensitive
payload.

The before/after hashes are what make the log useful: it does not merely say that something changed,
it says **what it changed from and to** in a form that can be checked against the entity's own
version history.

## 5. Why an administrator cannot quietly fix things

The security model gives `SystemAdministrator` no create or update access to `Approvals` (GOV-08), no
write access to `AuditLog`, and no read access to operational evidence, documents or financial
records at all. A technical administrator configures the platform, provisions users and works the
error queue; none of that requires reading a client's photographs, so they cannot. Business
master-data administration is a separate role (`BusinessAdministrator`) which also opens no
evidence, no documents and no money. See `04-security-model.md`.

An override — waiving an evidence rule, certifying beyond a contract quantity — is recorded **as an
override**, with an approver and a reason, on the `Approvals` row (`IsOverride`, `OverrideReason`).
Silent override is the failure mode this design exists to prevent (SEC-05, R-30).
